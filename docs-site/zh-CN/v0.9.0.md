# v0.9.0（2026-09-13）

v0.9.0 收口了 v0.8.0 之后发现的安全与上传边界缺口：上传现在登记自己创建的对象，Storage 策略审计
跟随代码而不是写死的 bucket 名，server-only 表与函数上所有客户端可达的写/执行路径都被收回。

## 亮点

- **上传对象元数据**：新增 `031_upload_objects.sql` 的 `public.upload_objects`，每次 `put` 一行
  （bucket、object key、所有者、字节数、MIME、sha256、状态）。`status = 'active'` 即
  「数据库认为这个对象应该存在」，因此可把 active 集合与 bucket 实际列表做双向差集找孤儿。
  上传流程改为 `put → 落元数据 → 回写业务表`；元数据写失败即删除对象并返回 `uploadFailed`，
  不再留下没有登记的公开对象。
- **Storage 策略审计跟随代码**：`src/lib/security/storage-policies.ts` 从 `src/**` 发现所有被引用的
  bucket、从迁移最终态推导生效的 `storage.objects` 策略，再做交叉验证。未登记 bucket、没有建行迁移、
  没有生效策略、写/读策略未钉住 `bucket_id` 与 `auth.uid()`、私有 bucket 出现公开读、
  公共读 bucket 无法读取，全部失败封闭。
- **`SECURITY DEFINER` 执行权限收回**：`028_revoke_security_definer_execute.sql` 收回
  `cleanup_old_notifications()`、`cleanup_old_webhook_events()`、`cleanup_old_email_worker_runs()`
  与 `log_audit_action()` 对 `PUBLIC` / `anon` / `authenticated` 的 `EXECUTE`。此前匿名调用者
  可以直接 `rpc` 触发保留期清理删除线上数据，或 `rpc` 伪造审计日志。
- **审计日志写入面收口**：`029_audit_logs_write_lockdown.sql` 删除遗留的
  `"Audit logs insertable by authenticated users"` 策略（对写入行内容零约束），并收回
  `anon` / `authenticated` 的表级 INSERT/UPDATE/DELETE/TRUNCATE。此前任意登录用户可
  `POST /rest/v1/audit_logs` 伪造 `user_id` 指向他人的审计记录（本地复现为 HTTP 201）。
  服务端 `appendAuditLog()` 与 `log_audit_action()` 走 `service_role`，不受影响。
- **Webhook 幂等改为租约模型**：`030_webhook_event_idempotency.sql` 把唯一键收窄为
  `(provider, event_id)` 并新增 `attempts` / `last_attempt_at`。Stripe 是 at-least-once 投递，
  而旧处理器先执行全部副作用再落日志，重投会重复写订阅、重复发通知。现在
  `claim_webhook_event()` 原子占位，重复投递返回 `duplicate` 与 `200` 且不执行副作用，
  副作用失败回 `500` 让下一次 Stripe 重试可重新占位。
- **`service_role` 边界清单门禁**：`src/lib/security/admin-client-boundary.ts` 清点每一个
  `createAdminClient()` 调用点（30 个模块 / 83 个调用点）及其 surface、授权模型与必须保留的源码证据。
  新路由 import 一次 admin client 已无法绕过评审。
- **RLS 回归门禁修复**：`pnpm check:rls` 原先把策略名按单个单词截断，35 条策略只校验了 24 条。
  现在由 `src/lib/security/rls-coverage.ts` 的最终态模型与本地 `pg_policies` 逐条一致
  （35/35，双向零差集），并对未分类表失败封闭。
- **邮件 worker 记录保留期**：`027_email_worker_runs_retention.sql` 新增
  `cleanup_old_email_worker_runs()`，90 天保留期（与 `notifications` / `webhook_events` 对齐），
  带守卫的每周 `pg_cron` 任务在未安装 `pg_cron` 的环境自动跳过。

## 升级说明

1. 按顺序应用迁移 `027`–`031`。五个迁移都是追加式的；`026` 及更早的基线保持 SHA-256 固定，不可改写。
2. **`030` 与 `031` 的顺序很关键。** 两者都改变了应用与 schema 的耦合方式：必须先迁移、再部署。
   回滚时先回滚应用，再单独决定 schema 是否回退。
3. 权限收窄是有意为之，不要为了让旧客户端恢复而重新放开：现在收到 `permission denied` 的客户端密钥，
   按定义就是在使用一条因为可伪造而被关闭的路径。
4. `cleanup_old_email_worker_runs()` 只在安装了 `pg_cron` 的环境自动执行。

## 已知限制

上传元数据表记录的是应用写入的内容；绕过应用直写 bucket 的对象不会出现在表里，这正是
`docs/db/upload-metadata.md` 中巡检 SQL 的用途。反向孤儿巡检（bucket 列表 → 元数据差集）尚未实现为
定时任务。生产仍需应用五个迁移并记录 smoke 结果。
