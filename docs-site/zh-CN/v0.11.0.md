# v0.11.0（2026-09-22）

v0.11.0 把两件事收口：数据的生命周期，以及发布链路本身。「删除账户后 30 天内删除或匿名化个人数据」
和「每次发布前所有检查都会跑」——这两条此前只写在文字里的承诺，现在都由代码、迁移和门禁兜住；
文字与实现一旦分叉，构建直接失败。

本版本**新增两条数据库迁移**（`032`、`033`），必须**先迁移、后部署应用**。

## 亮点

- **擦除先于删号**：`032_data_retention_erasure.sql` 新增 `erase_user_data(uuid)`——删除携带
  `ip_address` 的 `api_usage` 行；按本人邮箱删除 `contact_messages`（这张表根本没有外键）；
  匿名化 `audit_logs`：`user_id` 与指向本人的 `entity_id` 置空、`metadata` 剔除 PII 键，
  但「发生过某个动作」这一事实保留。纯 `ON DELETE CASCADE` 三类都覆盖不到。
  `src/lib/account/deletion.ts` 固化唯一正确的顺序：擦除失败即中止并**保留账户**（可重试）；
  删号后的审计补记失败只记日志、不把成功报成失败——因为账户已经删不掉地删了。
- **上传对象活过账户删除**：`033_upload_object_orphan_audit.sql` 把 `upload_objects.owner_id`
  改为可空、外键改为 `on delete set null`。这张表的级联删除恰好抹掉了「provider 删除失败」的
  唯一线索，而对象本身仍在 bucket 里公开可读。三个新增的 `service_role` 专属函数
  （`upload_object_is_referenced`、`list_user_objects_for_erasure`、`find_orphan_upload_objects`）
  回答「这个能删吗」——引用判定用后缀相等（`right(url, length(key)+1) = '/' || key`），
  因为 `_` 在 `LIKE` 里是通配符，而 `includes()` 会把 `xavatars/u/f.png` 也当成引用。
  删掉一个人的账户不会弄坏另一个人的团队封面图。
- **「危险区域」终于有了实现**：设置页的这部分文案翻译好了放了好几个月，背后没有任何组件。
  现在 `deleteAccountAction` 在服务端独立校验确认短语与会话归属、走频率限制、清理对象、擦除数据、
  删号、全局登出并 revalidate。
- **保留期只有一个事实源**：`src/lib/privacy/data-policy.ts` 登记保留天数、cron 任务名、
  擦除数据面、PII 键与确认短语，40 条契约测试把它与迁移 SQL、`docs/db/retention.md`、
  两份语言文件、生成的数据库类型双向钉死。Mock 客户端镜像同一套擦除语义，因此 E2E 跑的是真实顺序。
- **可观测性补的是盲区，不是文档**：`x-request-id` 由 `src/proxy.ts` 解析或生成
  （拒绝 CR/LF、制表符、空格与超过 128 字符，避免日志注入）并在重定向分支同样回写；
  16 个 Server Action 去掉了裸 `console.*`。`/api/cron/digest` 从未出现在 `vercel.json` 里，
  也就是说生产上摘要邮件早就静默停摆了。`email.backlog` 与队列拉取共用同一份类型清单。
  存储指标新增 `upload.request.completed`——provider 写入成功但元数据回写失败并回滚的**用户可见失败**，
  此前在指标里记成 `success`。缺失 `RESEND_API_KEY` 时邮件失败率告警一条样本都没有，
  现在立即以 `reason=not-configured` 结束。`ops.supabase.restore` 把 `escalate`/`skipped` 记为 `0`，
  于是按「计数 > 0」配置的告警永远不可能触发；现在所有终态都经由同一出口上报一条计数样本。
- **发布工程**：E2E 拆成两个 shard，各自拥有独立 dev server；覆盖率测试移到独立 job，
  `Build` 与 `E2E` 只等 lint；Playwright 浏览器进缓存；PR 的过期运行自动取消。
  新增每日 02:17 UTC 的 `smoke-main` 定时任务，比对生产版本与 `package.json`。
  新增门禁：`check:release-tag`、`check:production-smoke`、`check:gates`（要求每个 `check:*`
  都同时出现在 `check-all.sh` **和**某个 workflow 中，否则必须登记仍然成立的理由——它抓到了
  `check:agents` / `check:docs` 在 CI 从未执行）、`check:workflows`、`check:codeql`、`check:secrets-scan`。
- **内部错误码不再露出到界面**：`action-result.ts` 写明「失败时 `error` 是 i18n 键、客户端经
  `ta(error)` 翻译」，但 `fail(error: string)` 只是 `string`，没有任何机制守住这句话。
  四处调用点把 `projectNotFound` 直接当文案渲染，MFA 页在 challenge 失败时更是直接透出
  Supabase 的英文原始 message。新增门禁 `pnpm check:action-errors`：从产出侧提取所有错误码
  （`fail("code")`、`fail(expr ?? "code")` 兜底、zod 校验器的末位字符串实参），要求它在
  **每个** locale 都有键、且各 locale 文案不得逐字相同；消费侧禁止把 `result.error` /
  `authErrorKey(err)` 原样放进 `title` / `description`。首轮实测 42 个错误码，无需任何豁免。
- **第一条能证明「中文用户看到中文」的 E2E**：原有的两条语言切换用例只验证了能打开菜单，
  以及选择 English（它就是默认语言）后写入了 `app-locale` cookie。即使 zh-CN 消息完全加载失败，
  页面会安静退回英文，两条断言照样通过。新增用例把 `简体中文` 选到底，同时断言 cookie、
  `<html lang>`、首屏中文 Badge，以及英文原文不再出现。
- **漏翻译从此是构建失败**：`pnpm check:locales` 只比对 en 与 zh-CN 的**键集合**，所以「加了键、
  值还是英文」和「翻译好了」在构建上是同一个颜色——`settings.sections.security.title` 一直是
  `"Security"`，而同级的 `danger` 分区早就写着「危险区域」。门禁现在审**值**：`zh-CN` 文案里没有
  汉字即失败，值形如内部标识符（`projectNotFound`）另有一条更具体的规则。**消息数组按下标展开**：
  `home.statLabels`、`terms.sections[].content`、`blog.posts[].title` 由 `t.raw()` 直接渲染，
  占了文案的一半；键对称也精确到叶子路径，少一篇文章就是少一个键。实测每侧 1235 条叶子路径、
  2470 条文案受审、86 条值经 38 条登记（品牌名 / 占位符 / 结构字段）放行。写这道门禁时发现自己
  的判定就是错的：字面字符区间 `[豈-﫿]` 起点实为 U+8C48，整个谚文块被算作「含中文」，
  `한국어` 因此静默放行——已改为显式码点，并留一条谚文反例测试钉住。
- **一个概念只用一个词**：翻对了但用词不一致，键值审计看不见——同一个团队角色，成员列表里叫
  「拥有者」、错误提示里叫「所有者」，两边渲染的都是 `owner`。新增门禁 `pnpm check:glossary`：
  14 个术语按「英文侧命中该术语 → 中文侧不得出现禁止变体」判定，且只在指定译法**缺席**时才算违规，
  因为一句话可以同时翻译两个概念（`notification preferences and alerts` → 「通知偏好和提醒」，
  其中「提醒」译的是 `alerts`，不是漂移）。`docs/architecture/10-i18n.md` 的术语表与代码里的
  `GLOSSARY` 必须双向逐字相等，文档不能比规则更宽或更旧。按英文原值逐条核对全库后，真正的漂移只有
  两处——「账号」「拥有者」——已统一；首轮 271 次 (键, 术语) 比对，0 违规、0 豁免。
- **应用层不再使用物理方向类（D08）**：产品只有两个 LTR 语言，所以目标不是「支持 RTL」，
  而是 `mr-2` 与 `me-2` 在 LTR 下**渲染结果完全一致**、换过去零代价：应用层 74 处物理方向类
  已全部改为逻辑方向，并新增 `pnpm check:direction` 把应用层钉在 0 处（扫不到文件即失败）。
  两处残留是**登记**而非隐瞒：`src/components/ui/**` 里的 35 处（shadcn 基元，升级会被上游覆盖），
  以及 `translate-x-*` / `origin-left`——Tailwind v4 **根本没有逻辑等价物**。
  证明这次替换在视觉上无动的，不是截图而是两条事实：应用从不设置 `dir` 属性，两个语言因此都按
  `ltr` 计算，而 `ltr` 下 `margin-inline-start` 就是 `margin-left`；一次全新的生产构建被逐条解析，
  确认本次新写的 25 个逻辑类（74 处）各自仍产出一条规则、值函数与物理写法完全一致、只是换到行内轴。
  被静默丢弃的工具类（`rounded-sg`）不会报任何错，这正是该项检查要抓的失败模式。
  CI 的 Linux 视觉基线是后续确认，此处不声称已经跑过。
- **一个永远不会失败的门禁，比没有门禁更糟（D10）**：`check:a11y` 每轮都打印「✅ 无未标注的
  图标按钮」，而它的图标按钮规则**结构上不可能命中**——外层要求 children 里没有任何 2 个以上
  字母的连续串，内层又要求组件名（`MoreHorizontal`、`<svg`）存在。它还像同类门禁那样不打印任何
  计数器，于是这份空转一路活过了每一次绿色 CI。真实后果是 3 个 `size="icon"` 按钮长期没有任何
  可访问名称，屏幕阅读器只会念「按钮」。规则现在收进 `src/lib/ui/a11y-rules.ts` 纯函数，
  扫不到文件即失败封闭，输出 `scannedFiles / buttons / iconOnlyButtons`，并用 4 项变异测试
  证明它真的会失败；3 处标注全部复用已有消息键，不新增文案。
- **仪表盘从来没被审计过（D10）**：`e2e/a11y.spec.ts` 只访问 5 个公共页，从不进入登录后区域——
  那些未标注的图标按钮正是这样同时躲过两道门禁的。补上 9 个已认证页（共 14 条 axe 用例）后，
  当场抓到 3 处真实的 WCAG 1.4.3 违规：destructive 作为文字 3.76:1、muted 底上的 muted 文字 4.39:1、
  白字压 destructive 背景 3.6:1，全部低于正文要求的 4.5:1。修在 token 层而不是逐处改类名：新增
  `--destructive-text`（浅色 `#d72323`，5.06:1；深色 `#f87171`，6.4:1），因为 `--destructive` 的语义是
  「红底配浅色前景」，深色模式下它是暗红、当文字几乎看不见；同时压深浅色的 `--destructive` 与
  `--muted-foreground`。视觉基线只有 `pricing` 一张变化。**这里踩过一个坑**：容器并不等价于 CI——
  CI 的视觉步骤跑在 `ubuntu-latest` 宿主机上，两者子像素抗锯齿不同，同一份代码累计差 16353 px
  （约 1.0%）就超了 0.1% 阈值；容器内部自己比对永远 4/4，什么也证明不了。基线最终改用 runner
  自己产出的 `-actual.png`，`docs/testing.md` 里「用该容器生成基线」的错误流程也一并改掉。
- **被校验的文档，而不是被相信的文档**：ADR 索引与取代链、Mock 系统指南（18 张表、真实的
  `globalThis` 缓存模型、接入点是 `src/proxy.ts` 而非已退役的 `middleware.ts`）、provider 诊断
  （`pnpm provider:doctor`，9 个 provider / 28 个变量，**从不输出凭据值**）、贡献者测试矩阵、
  迁移回滚 runbook，各自配一道双向门禁；抽取结果为空时失败封闭。

## 升级说明

1. **先跑迁移。** `032_data_retention_erasure.sql` 与 `033_upload_object_orphan_audit.sql`
   必须先于应用部署。两者都是追加式变更（函数、两个部分索引、一次约束放宽），
   因此旧版本应用在新 schema 上照常工作，回滚保持只向前。
2. 新增的 SQL 函数都是 `security definer` + 空 `search_path`，只授予 `service_role`——
   与 `028` 的结论一致：此前客户端可以直接通过 `rpc()` 触发数据破坏。
3. `upload_objects.owner_id` 从此可空。`NULL` 的含义是「上传者账户已注销」，这些行正是
   `find_orphan_upload_objects()` 要报告的内容，所以不要把 owner 为空的行「清理」掉。
4. 账户删除从此是真正不可逆的操作。只用一次性测试账号验证。
5. `pnpm check:all` 变长了，推送前先跑。

## 已知限制

- **保留期仍未真正执行**。`003` / `014` / `027` / `032` 里的每周清理都被 pg_cron 存在性守卫包住，
  而本地与云端项目都没安装该扩展。迁移成功、门禁全绿、`/api/health` 正常——一行都没删。
  启用 pg_cron 需要 Supabase Dashboard 权限，属外部运维动作。在此之前
  `docs/db/retention.md` 的天数只能读作承诺，不能读作行为。
- `031` 之前直接写进 bucket、从未落 `upload_objects` 行的对象，孤儿清单看不见；
  要发现它们需要拿 provider 侧 `list()` 与数据库做集合差。
- `e2e/account-deletion.spec.ts` 故意不提交真实确认短语：Mock 的 `deleteUser` 是空操作，
  一旦提交成功会把后续用例共享的 mock 状态清空。
