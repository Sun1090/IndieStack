# v0.8.0 (2026-09-13)

v0.8.0 turns Web Push from an immediate best-effort send into a durable,
at-least-once channel with a retry queue and dead-letter visibility.

## Highlights

- **Persistent delivery queue**: new `026_push_delivery_attempts.sql` stores one
  row per `(notification_id, endpoint)` with `pending` / `sent` / `dead` status,
  attempt count, failure code and `next_attempt_at`. A unique key plus
  idempotent enqueue means a retry never re-sends to an endpoint that already
  succeeded, and one failing browser endpoint no longer fans out to the others.
- **Exponential backoff and retry cap**: transient failures are retried at
  60s then 2min (`60s × 2^(n-1)`, capped at 1 hour) up to 3 attempts including
  the first send, after which the row enters the dead-letter state.
- **Invalid endpoint handling**: a `404`/`410` from the push service revokes the
  local subscription immediately and dead-letters the row instead of retrying.
- **Retry worker**: `/api/cron/push-retry` runs every 15 minutes (batch of 50),
  is protected by `CRON_SECRET`, and returns sanitized counts only. The worker
  fails loudly when VAPID is unconfigured rather than silently dead-lettering.
- **Bounded queue retention**: each worker run prunes `sent` rows after 7 days
  and `dead` rows after 30 days, up to 1,000 rows per status. `pending` rows are
  never pruned, and the response reports deletion counts as `pruned`.
- **Observability**: `push.backlog` (alert threshold 500), `push.delivery.dead`,
  `push.endpoint.revoked`, `push.queue.pruned|prune_failed` and
  `cron.push-retry.completed|failed` metrics.

## Upgrade Notes

1. Apply migration `026_push_delivery_attempts.sql` — it is additive; no existing
   table is altered. Already-baselined migrations stay SHA-256 pinned.
2. Ensure `CRON_SECRET` exists in the deployment: the new cron route (and the
   existing digest/restore routes) returns `401` without it.
3. Browser push still requires `NEXT_PUBLIC_VAPID_PUBLIC_KEY` and the
   server-only `VAPID_PRIVATE_KEY`, plus an HTTPS production origin.
4. Delivery is now **at-least-once**. In rare cases (a process crash before the
   receipt is written) an endpoint may receive the same notification twice;
   the in-app notification remains the single source of truth, so clients should
   stay idempotent on `idempotencyKey`.

## Known Limitations

The retry and dead-letter chain is covered by unit tests and a local database
smoke run, but not yet by an end-to-end browser test — that is scheduled for the
next milestone. In production, verify the queue with a real `CRON_SECRET` call.
