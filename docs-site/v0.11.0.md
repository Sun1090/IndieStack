# v0.11.0 (2026-09-22)

v0.11.0 closes the loop on data lifetime and on the release pipeline itself. Two
promises that previously lived only in prose — "personal data is deleted or
anonymised within 30 days of account deletion" and "every check runs before we
ship" — are now backed by code, migrations and gates that fail the build when the
prose and the implementation drift apart.

This release **adds two database migrations** (`032`, `033`) and they must be
applied **before** the application is deployed.

## Highlights

- **Account erasure happens before the account is deleted**: `032_data_retention_erasure.sql`
  adds `erase_user_data(uuid)` — it deletes `api_usage` rows (which carry
  `ip_address`), deletes `contact_messages` by the owner's email (that table has no
  foreign key at all), and anonymises `audit_logs`: `user_id` and self-referencing
  `entity_id` go null, PII keys are stripped from `metadata`, while the fact that an
  action happened survives. Plain `ON DELETE CASCADE` covered none of the three.
  `src/lib/account/deletion.ts` enforces the one correct order: erasure failure
  aborts and keeps the account (retryable); a post-deletion audit write failure is
  logged but never reported as a failed deletion, because the user is already gone.
- **Upload objects now outlive the account that created them**:
  `033_upload_object_orphan_audit.sql` changes `upload_objects.owner_id` to nullable
  with `on delete set null`. Cascade on that row was destroying the only evidence
  that a provider-side delete had failed, while the object itself stayed publicly
  readable in the bucket. Three new `service_role`-only functions
  (`upload_object_is_referenced`, `list_user_objects_for_erasure`,
  `find_orphan_upload_objects`) answer "may I delete this?" correctly —
  reference detection compares by suffix (`right(url, length(key)+1) = '/' || key`)
  because `_` is a wildcard in `LIKE`, and `includes()` would accept
  `xavatars/u/f.png` as a reference. Deleting one account never breaks another
  account's team cover images.
- **A Danger Zone that actually exists**: the settings page shipped translated
  strings for months with no component behind them. `deleteAccountAction` now
  validates the confirmation phrase and session ownership server-side, rate-limits,
  cleans objects, erases, deletes, signs out globally and revalidates.
- **Single source of truth for retention**: `src/lib/privacy/data-policy.ts` holds
  retention days, cron job names, erasure surfaces, PII keys and the confirmation
  phrase; 40 contract tests pin it against migration SQL, `docs/db/retention.md`,
  both locale files and the generated database types. The Mock client mirrors the
  same erasure semantics so E2E exercises the real ordering.
- **Observability gaps closed, not just documented**: `x-request-id` is parsed or
  generated in `src/proxy.ts` (rejecting CRLF, tabs, spaces and >128 chars to avoid
  log injection) and echoed on redirects; 16 Server Actions lost their bare
  `console.*`. `/api/cron/digest` was never listed in `vercel.json`, so digest mail
  had silently stopped running in production. `email.backlog` and the queue pull now
  share one type list. Storage metrics gained `upload.request.completed` because a
  provider write that succeeds and then fails the metadata write-back used to be
  counted as a success. Missing `RESEND_API_KEY` produced zero samples for the email
  failure-rate alert; it now reports `reason=not-configured` immediately.
  `ops.supabase.restore` counted `escalate`/`skipped` as `0`, so a `> 0` alert could
  never fire — every terminal state now emits one count sample.
- **Release engineering**: E2E runs as two shards with per-shard dev servers;
  coverage moved to its own job so `Build` and `E2E` wait only on lint; Playwright
  browsers are cached; PR runs cancel stale ones. A scheduled `smoke-main` job checks
  the deployed version against `package.json` daily at 02:17 UTC. New gates:
  `check:release-tag`, `check:production-smoke`, `check:gates` (every `check:*` must
  run in `check-all.sh` **and** a workflow, or carry a still-true exemption — this one
  caught `check:agents` / `check:docs` never running in CI), `check:workflows`,
  `check:codeql`, `check:secrets-scan`.
- **Error codes stop leaking into the UI**: `action-result.ts` documents that a failed
  action's `error` is an i18n key the client translates with `ta(error)`, but
  `fail(error: string)` is just a `string`, so nothing enforced it. Four call sites
  rendered `projectNotFound` as user-visible text, and the MFA page showed Supabase's
  raw English message on challenge failure. New gate `pnpm check:action-errors`
  extracts every producible code (`fail("code")`, `fail(expr ?? "code")`, the last
  string argument of a zod validator) and requires a key in **every** locale whose
  value is not byte-identical across locales, and rejects raw rendering in
  `title` / `description`. First run: 42 codes, zero exemptions needed.
- **First E2E that proves Chinese users see Chinese**: the two existing
  language-switch tests opened the menu and asserted the `app-locale` cookie after
  selecting English — the default. If zh-CN messages failed to load at all, the page
  would fall back silently and both tests would still pass. A new case selects
  `简体中文` and asserts the cookie, `<html lang>`, the rendered Chinese hero badge,
  and that the English original is gone.
- **A missing translation is now a build failure**: `pnpm check:locales` compared the
  en and zh-CN key *sets*, so a key whose Chinese value was still English was
  indistinguishable from a finished translation — `settings.sections.security.title`
  read `"Security"` while its sibling `danger` section had long read 「危险区域」. The gate
  now checks values: a `zh-CN` string with no Han character fails, and a value shaped like
  an internal identifier (`projectNotFound`) fails a more specific rule. Message **arrays**
  are expanded by index, because `home.statLabels`, `terms.sections[].content` and
  `blog.posts[].title` are rendered straight from `t.raw()` and account for half of the
  copy; key symmetry is now leaf-path exact, so a dropped blog post is a missing key.
  1235 leaf paths per locale, 2470 values audited, 86 exempted through 38 registered
  brand/placeholder/structural-field entries. Writing it exposed a bug in the rule itself:
  the literal range `[豈-﫿]` actually starts at U+8C48, so the whole Hangul block counted
  as Chinese and `한국어` passed silently — the pattern is now explicit code points, with a
  Hangul counter-example pinned by a test.
- **One concept, one word**: a correct-but-inconsistent translation is invisible to a key/value
  check — the same team role was 「拥有者」 in the member list and 「所有者」 in the error message, both
  rendering `owner`. New gate `pnpm check:glossary` pins 14 terms as "the English copy uses this
  term → the Chinese copy must not use a registered variant", and only when the approved term is
  *absent*, because one sentence can legitimately render two concepts
  (`notification preferences and alerts` → 「通知偏好和提醒」, where 「提醒」 translates `alerts`).
  The table in `docs/architecture/10-i18n.md` must match the `GLOSSARY` constant in both directions,
  so the document cannot be looser or older than the rule. Checking every key against its English
  source turned up exactly two real drifts — 「账号」 and 「拥有者」 — now unified;
  first run: 271 (key, term) comparisons, zero violations, zero exemptions.
- **Physical CSS classes retired from app code (D08)**: the product speaks two LTR languages,
  so "RTL support" is not the point — `mr-2` vs `me-2` render *identically* in LTR, so the 74
  physical-direction classes in app code (33 files) became logical ones for free, and
  `pnpm check:direction` now keeps app code at zero (failing closed when it scans no files).
  Two residues are registered rather than hidden: 35 occurrences inside `src/components/ui/**`
  (shadcn primitives, overwritten on upgrade) and `translate-x-*` / `origin-left`, for which
  Tailwind v4 has **no logical equivalent** at all. What proves the swap was visually inert: the
  app sets no `dir` attribute, so both locales compute as `ltr`, where `margin-inline-start`
  resolves to `margin-left`; and a fresh production build was parsed to confirm the 25 newly
  written logical classes (74 occurrences) still each emit a rule — the value function is
  identical to the physical one, only on the inline axis. A silently dropped utility
  (`rounded-sg`) leaves no error, which is exactly the failure this check looks for. CI's Linux
  visual baselines remain the downstream confirmation; they are not claimed as passed here.
- **A gate that could not fail was worse than no gate (D10)**: `check:a11y` printed
  「✅ no unlabeled icon buttons」 every run while its icon-button rule was **structurally
  unreachable** — the outer branch required the children to contain no run of 2+ letters, the
  inner test required a component name (`MoreHorizontal`, `<svg`) to exist. Unlike its siblings
  it printed no counters, so the idleness survived every green CI. Three real `size="icon"`
  buttons had been shipping with no accessible name at all; screen readers announced only
  「button」. The rule now lives in `src/lib/ui/a11y-rules.ts` as pure functions, fails closed
  when it scans nothing, prints `scannedFiles / buttons / iconOnlyButtons`, and is proven to be
  capable of failing by four mutation tests. The three labels reuse existing message keys.
- **The dashboard had never been audited (D10)**: `e2e/a11y.spec.ts` only visited 5 public pages and
  never entered the signed-in area — which is exactly how those unlabeled icon buttons survived. With
  9 authenticated pages added (14 axe cases), three real WCAG 1.4.3 failures surfaced immediately:
  destructive-as-text 3.76:1, muted text on a muted surface 4.39:1, white on a destructive background
  3.6:1 — all under the 4.5:1 body requirement. Fixed in the token layer, not per component: a new
  `--destructive-text` (`#d72323` light, 5.06:1; `#f87171` dark, 6.4:1) because `--destructive` means
  「red surface, light foreground」 and is a near-invisible dark red as text in dark mode, plus darker
  light-mode `--destructive` and `--muted-foreground`. Only the `pricing` baseline moved — and the
  container is **not** equivalent to CI: its visual step runs on the `ubuntu-latest` host, and the two
  differ in subpixel antialiasing by 16,353 px (~1.0%) on this very code, blowing the 0.1% budget.
  Container-vs-itself passing 4/4 proved nothing. The baseline now comes from the runner's own
  `-actual.png`, and `docs/testing.md` no longer recommends generating baselines in the container.
- **Documentation that is checked, not trusted**: ADR index and supersession,
  the mock-system guide (18 tables, real `globalThis` cache model, `src/proxy.ts`
  instead of the retired `middleware.ts`), provider diagnostics
  (`pnpm provider:doctor`, 9 providers / 28 variables, never prints a value),
  the contributor testing matrix and the migration rollback runbook each gained a
  bidirectional gate that fails closed when the extraction itself comes up empty.

## Upgrade Notes

1. **Run migrations first.** Apply `032_data_retention_erasure.sql` and
   `033_upload_object_orphan_audit.sql` before deploying the app. Both are additive
   (functions, two partial indexes, one constraint relaxation), so an older app
   version keeps working against the new schema and rollback stays forward-only.
2. The new SQL functions are `security definer` with an empty `search_path`, granted
   to `service_role` only — same hardening conclusion as `028`, which found the
   client could previously trigger data-destroying functions through `rpc()`.
3. `upload_objects.owner_id` is nullable from now on. `NULL` means "the account that
   uploaded this is gone"; those rows are exactly what
   `find_orphan_upload_objects()` reports, so do not "clean up" null owners.
4. Account deletion is now genuinely destructive and irreversible. Test it with a
   throwaway account only.
5. `pnpm check:all` grew; run it before pushing.

## Known Limitations

- **Retention is not yet executing.** Every weekly cleanup in `003` / `014` / `027` /
  `032` is wrapped in a `pg_cron` existence guard, and neither the local nor the
  linked project has that extension installed. The migrations succeed, the gates are
  green, `/api/health` is fine — and not one row is deleted. Enabling pg_cron needs
  Supabase Dashboard access, an external operations action. Until then read the
  retention days in `docs/db/retention.md` as a commitment, not a behaviour.
- Objects written to a bucket before `031`, which never got an `upload_objects` row,
  are invisible to the orphan list; finding them requires a provider-side `list()`
  diff against the database.
- `e2e/account-deletion.spec.ts` deliberately never submits the real confirmation
  phrase: the Mock `deleteUser` is a no-op and a successful submission would wipe
  shared mock state for the rest of the suite.
