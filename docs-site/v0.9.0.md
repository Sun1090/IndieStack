# v0.9.0 (2026-09-13)

v0.9.0 closes the security and upload-boundary gaps found after v0.8.0: uploads
now register what they create, the storage policy audit follows the code instead
of a hardcoded bucket name, and every client-reachable write and execute path on
server-only tables and functions is locked down.

## Highlights

- **Upload object metadata**: new `031_upload_objects.sql` adds
  `public.upload_objects`, one row per `put` (bucket, object key, owner, byte
  size, MIME, sha256, status). `status = 'active'` is exactly "the database
  believes this object exists", so the active set can be diffed against the real
  bucket listing in both directions to find orphans. Uploads now run
  `put → record metadata → update business row`; a metadata failure deletes the
  object and returns `uploadFailed` instead of leaving an unregistered public
  object behind.
- **Storage policy audit that follows code**: `src/lib/security/storage-policies.ts`
  discovers every bucket referenced under `src/**` and derives the effective
  `storage.objects` policies from the migration final state, then cross-checks
  both. Undeclared buckets, unversioned buckets, unpoliced buckets, unscoped
  write/read policies, public read on a private bucket and an unreadable public
  bucket all fail closed.
- **`SECURITY DEFINER` execute revoked**: `028_revoke_security_definer_execute.sql`
  removes `EXECUTE` on `cleanup_old_notifications()`,
  `cleanup_old_webhook_events()`, `cleanup_old_email_worker_runs()` and
  `log_audit_action()` from `PUBLIC` / `anon` / `authenticated`. Previously any
  anonymous caller could `rpc` a retention cleanup into deleting live rows or
  `rpc` a forged audit entry.
- **Audit log write lockdown**: `029_audit_logs_write_lockdown.sql` drops the
  legacy `"Audit logs insertable by authenticated users"` policy (which validated
  nothing about the row) and revokes table-level INSERT/UPDATE/DELETE/TRUNCATE
  from `anon` / `authenticated`. Any logged-in user could previously
  `POST /rest/v1/audit_logs` and forge records with someone else's `user_id`
  (reproduced locally as HTTP 201). Server-side `appendAuditLog()` and
  `log_audit_action()` run as `service_role` and are unaffected.
- **Webhook idempotency as a lease**: `030_webhook_event_idempotency.sql` narrows
  the unique key to `(provider, event_id)` and adds `attempts` /
  `last_attempt_at`. Stripe delivery is at-least-once, but the handler used to
  run every side effect before logging, so a retry duplicated subscription writes
  and notifications. `claim_webhook_event()` now atomically claims the event,
  duplicate deliveries return `duplicate` with `200` and no side effects, and a
  failed side effect returns `500` so the next Stripe retry can re-claim it.
- **`service_role` inventory gate**: `src/lib/security/admin-client-boundary.ts`
  enumerates every `createAdminClient()` call site (30 modules, 83 call sites)
  with its surface, authorization model and required source evidence. New routes
  importing the admin client can no longer skip review unnoticed.
- **RLS regression gate fixed**: `pnpm check:rls` previously truncated policy
  names on the first word, so 35 policies were validated as 24. The final-state
  model in `src/lib/security/rls-coverage.ts` now matches local `pg_policies`
  exactly (35/35, zero-diff both ways) and fails closed on any unclassified table.
- **Email worker retention**: `027_email_worker_runs_retention.sql` adds
  `cleanup_old_email_worker_runs()` with a 90-day window (aligned with
  `notifications` and `webhook_events`) and a guarded weekly `pg_cron` schedule
  that silently skips environments without `pg_cron`.

## Upgrade Notes

1. Apply migrations `027`–`031` in order. All five are additive; migrations `026`
   and earlier stay SHA-256 pinned and must not be rewritten.
2. **Order matters for `030` and `031`.** Both change how the application couples
   to the schema, so migrate first, then deploy. On rollback, revert the
   application first and decide separately whether the schema moves back.
3. The grants changes are intentional and should not be reverted to unblock
   an old client: client keys that now get `permission denied` are, by definition,
   using a path that was closed for being forgeable.
4. `cleanup_old_email_worker_runs()` only auto-runs where `pg_cron` is installed.

## Known Limitations

The upload metadata table records what the application wrote; objects written
directly to the bucket bypass the table, which is what the reconciliation query
in `docs/db/upload-metadata.md` is for. Reverse orphan reconciliation
(bucket listing → metadata diff) is not yet a scheduled worker. Production still
needs to apply the five migrations and record a smoke run.
