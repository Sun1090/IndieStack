# v0.10.0 回滚 Runbook

> 回滚优先恢复服务，不自动回滚数据库。数据库逆向迁移可能造成数据丢失，必须经过 DBA 与发布负责人共同决定。

## 触发条件

触发条件包括：持续 5xx、认证/支付/上传关键路径不可用、数据完整性风险、迁移导致请求失败、错误率超过发布前基线两倍且持续 5 分钟，或 health check 连续失败。本版本是纯 UI 系统收口，前端的典型故障形态是**页面外观退化或交互不可用**（导航点不开、深色模式闪烁、首屏空白）而不是数据问题。

## 决策树

1. **代码回滚即可修复**：将 Vercel/部署平台切换到上一个已验证 deployment；保留当前数据库 schema，确认旧代码能兼容新增列。
2. **迁移不可兼容**：先暂停写入或关闭受影响 feature flag，再恢复应用；不得直接执行 `down` SQL。
3. **数据损坏或误写**：停止相关 worker，保留日志和数据库快照，按备份恢复演练流程处理，并记录影响范围。
4. **仅 provider 故障**：保持应用版本，关闭 provider 开关，启用已验证 fallback；不要为了外部服务故障回滚无关代码。
5. **仅样式/交互退化（本版本特有）**：优先整包回滚到上一个 deployment，而不是热改 CSS——`globals.css`
   的 token 与 `@theme` 映射是构建期产物，运行时改类名无法保证与构建一致。

## 操作步骤

```bash
# 记录当前状态（先保存，不要覆盖证据）
date -u
curl -fsS "$PRODUCTION_URL/api/health" > /tmp/indiestack-health-before-rollback.json
# 在部署平台选择上一个已验证 deployment / commit SHA
# 回滚后再次执行
a=0; while [ "$a" -lt 3 ]; do curl -fsS "$PRODUCTION_URL/api/health"; a=$((a+1)); sleep 10; done
pnpm health:check -- "$PRODUCTION_URL"
```

实际平台切换必须由有权限的发布人员执行；命令中的 URL、deployment ID 和输出必须写入 incident 记录。

## 回滚后验证

- `/api/health` 返回成功且版本符合预期；
- 匿名首页与登录流程可用；
- 最近一次迁移状态明确，无半完成迁移；
- 5xx、延迟、Sentry、队列积压恢复到发布前基线；
- 新写入和后台 worker 没有重复执行；
- 至少一条关键业务 smoke test 通过；
- 浅色与深色首屏都不再出现主题闪烁，375px / 768px 导航可达；
- 通知相关 provider 若被关闭，用户可见降级行为已记录。

## 迁移处理原则

迁移必须先做备份/快照并确认孤儿数据。只有存在经过测试的逆向迁移、明确的锁定窗口和 DBA 批准时才允许逆向迁移；否则采用前向修复迁移。每次回滚都要更新事故记录、CHANGELOG 的已知问题和后续修复 issue。

## v0.10.0 回滚补充

本版本**没有新增数据库迁移**（最新仍是 `031_upload_objects.sql`），因此回滚复杂度低于 v0.9.0：

- **数据库保持向前 schema 即可**。本版本不读写任何新表/新列，回滚应用 deployment 后数据库无需任何动作；
  `031` 及更早的迁移继续保留，不需要也不应该逆向迁移。
- **不要为了“回滚 UI”去改 `globals.css` 的 token 值**。状态色与图表色的语义映射是构建期产物，
  手工改运行时样式会与构建产物不一致，且 `pnpm check:tokens` 会立刻失败。要退样式请整包回滚。
- **删除的旧模块不需要恢复**。`page-loader.tsx` / `loading-state.tsx` 在回滚前就是零引用，
  回滚到上一版本时它们自然回到上一版本的代码，无需手工补文件。
- **若回滚后 404 / 空态 / 加载态出现样式错乱**，说明 deployment 与静态资源版本不匹配（CDN 缓存了
  新版本的 CSS chunk）。先确认 deployment 切换完整、再清 CDN，不要修改代码。
- 若怀疑是深色模式首屏脚本被 CSP 阻断导致的闪烁，回滚不是唯一手段：可先确认 CSP nonce 是否正确下发，
  修复后走**前向修复**，因为首屏脚本本身只影响显示时机、不影响数据。
