# 发布标签台账：哪些 CHANGELOG 版本还没有 git tag，以及为什么

> 这份台账回答一个具体问题：**读 `CHANGELOG.md` 会以为存在 11 个可 `git checkout` 的发布，
> 而仓库里只有 1 个。** 逐个版本的理由在这里，`pnpm check:changelog-tags` 强制两者对账。

## 现状

- `CHANGELOG.md` 声明 **11** 个已发布版本（0.1.0 – 0.11.0），合计约 210 条内容。
- 仓库里实际存在的 tag 与 GitHub Release：**只有 `v0.6.0`**（2026-09-12）。
- 因此有 **10** 个版本处于「CHANGELOG 说发布了、仓库里没有 tag」的分叉状态。

## 两组原因**不同**，所以不合并成一条

| 版本 | 章节日期 | 条目 | 原因 |
|---|---|---|---|
| `0.1.0` | 2026-07-19 | 25 | 标签纪律尚不存在 |
| `0.2.0` | 2026-08-23 | 23 | 标签纪律尚不存在 |
| `0.3.0` | 2026-08-23 | 15 | 标签纪律尚不存在 |
| `0.4.0` | 2026-09-05 | 22 | 标签纪律尚不存在 |
| `0.5.0` | 2026-09-05 | 17 | 标签纪律尚不存在 |
| `0.7.0` | 2026-09-12 | 19 | 生产已部署，发布证据未闭合 |
| `0.8.0` | 2026-09-13 | 3 | 生产已部署，发布证据未闭合 |
| `0.9.0` | 2026-09-13 | 12 | 生产已部署，发布证据未闭合 |
| `0.10.0` | 2026-09-13 | 7 | 生产已部署，发布证据未闭合 |
| `0.11.0` | 2026-09-22 | 33 | 生产已部署，发布证据未闭合 |

### 组一：`0.1.0`–`0.5.0` —— 纪律当时还不存在

tag / Release Notes 自动化门禁 **J07** 是在 **v0.6.0 那个周期**落地的
（见 `docs/roadmap-0.6.0.md` 的 J07 条目），而 `v0.6.0` 恰好就是**唯一一个**有 tag 的版本。
两件事对得上，不是巧合：这 5 个版本发布时，仓库里还没有「打 tag 前要先跑发布门禁」这件事。

**为什么不补打**：补打等于**伪造从未发生过的发布证据**——那 5 个版本从来没有经过
现在这套门禁。给它们打上 `v0.1.0` 这样的 tag，只会让后来人以为「这个版本被门禁校验过」。

### 组二：`0.7.0`–`0.11.0` —— 纪律已在，证据未闭合（**有意的克制**）

生产确实部署过（`0.11.0` 的生产部署记录在 `docs/roadmap-0.12.0.md` 开头），而打 tag 的前置是
**发布证据**：

- 账户删除端到端演练 —— 需要可牺牲的隔离账号与云端 Supabase 凭据；
- commit 归属证据 —— 需要能读全部历史的 CI；
- 带 commit 的生产构建 —— 需要 Vercel 部署权限与 build 配额。

这三项全部是 **B01 / B02 / B03**，全部卡**外部权限**。所以 tag **刻意不打**：
**没有证据就等于没做**，而打 tag 是对外声明「做完了」。

## 门禁怎么保证这件事不再变回「静悄悄」

`pnpm check:changelog-tags`（规则在 `src/lib/release/changelog-tag-reconciliation.ts`）：

- CHANGELOG 的每个已发布版本，要么有对应 tag，要么在 `MISSING_TAG_LEDGER` 里登记理由；
- **反方向也判**：有 tag 但 CHANGELOG 没写章节 → 红（同一类分叉，相反方向）；
- **登记过期也红**：某版本已经有 tag 了，登记却还在 → 红。
  **这是这份台账的自我清理机制**：将来 B01/B02/B03 闭合、tag 补上之后，
  必须回来删掉对应条目，否则门禁会红——**一件做完的事不该继续看起来没做完。**
- 一条版本都没解析出来 → 红（解析失效应出声）。

## 将来该怎么做

1. B01/B02/B03 的证据闭合后，按发布流程补 tag（走 `.github/workflows/release.yml`，
   它会强制跑 `pnpm check:all` 与 `pnpm check:release-tag`）；
2. **删掉** `MISSING_TAG_LEDGER` 里对应的条目（不删会红）；
3. 更新本文件与 CHANGELOG 开头的说明；
4. `0.1.0`–`0.5.0` 是否补打 tag，是一次**独立的产品决策**：补打等于承认它们通过了
   从未存在过的门禁。本文件不替这个决定表态，只要求它被显式记录。
