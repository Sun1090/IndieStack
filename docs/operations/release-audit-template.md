# 发布核对模板 / Release Audit Template

> 用途：为每个版本产出两类文件的**方法**——`release-gap-audit-v<版本>.md`（冻结与交付缺口审计）
> 与 `release-exit-report-v<版本>.md`（任务池逐条退出核对）。
> 两者用的是同一套判定规则，只是覆盖面不同：前者面向「这次发布还差什么」，
> 后者面向「任务池里的 100 项各自站在哪一档」。
>
> 来历：v0.6.0 的退出报告（`release-exit-report-v0.6.0.md`）是第一次把这套方法跑完整，
> 过程中发现 roadmap 正文的「（完成：…）」标注与开头进度汇总无人维护、与代码相反，
> 只能重新逐条核对。缺口审计系列则在 v0.10.0 之后断档（v0.11.0 的这份由 D03 补）。
> **方法只存在于某一个人的记忆里，就等于不存在**——这份模板把它写下来。

## 输入清单

开工前一次性列全，缺哪件就说明哪件没做（不要用「我记得做过」代替）：

| 输入 | 用来确定 |
| ---- | -------- |
| `package.json` 版本 + `git tag -l` | 版本号是否等于已发布版本；tag 存不存在 |
| `CHANGELOG.md` 的 `[<版本>]` 章节 | **本版本的真实范围**（不是 runbook 的记忆） |
| `docs/roadmap-<版本>.md`（若存在）或上一版任务池 | 退出条件与条目 ID |
| `docs/operations/{release,rollback}-runbook-v<版本>.md`、`production-smoke-v<版本>.md` | 冻结状态、未执行步骤、冒烟各行 |
| `docs/progress.md` 的同日期条目 | 当时留下的运行证据 |
| `supabase/migrations/` + `migration-manifest.json` | 本版是否含迁移、迁移号 |
| `.github/RELEASE_CHECKLIST.md` + `scripts/check-release-docs.js` | 发布产物是否按版本接线 |
| CI 运行记录（`gh run list` / `gh pr checks` / artifact 指纹） | 门禁是否在 CI 真的跑过、证据是否可下载 |

## 五条硬规则

1. **三档状态，每档要什么证据写死。**
   - 达成：可复现命令 + 输出（或门禁名），或带日期的执行记录（UTC 时间、命令、对象、结论）。
   - 部分达成：必须说清「哪一半没有」以及**为什么没有**（缺权限？缺决策？没写？）。「有待验证」不是缺口。
   - 未达成：允许，但必须落到下一版任务池并给编号。
2. **「文档已写」永远不算证据。** 一句承诺要能翻译成一条命令：`pnpm check:x`、
   `node scripts/...`、`supabase migration list --linked`，或者一份 `docs/operations/drills/*.sql`
   的真实运行结果。写不出命令的条目就还是承诺。
3. **门禁本身也要复核可达性。** 每条门禁至少问一次「故意做坏会不会红」，并把结果记下来
   （删掉某行 → 期望的错误码）。一个永远不会失败的门禁比没有门禁更糟：它凭空制造信心，
   而且不会像缺门禁那样引起注意。反例见 `check:a11y`（v0.11.0 复核时结构上不可能命中）
   与 `Production Smoke` 的手动作业（每天在空参数上失败，红色落在错误的作业上）。
4. **范围由 CHANGELOG 章节生成，ID 必须带池子名。** 先按章节抽出所有
   `（X99）`/`（X99 / X98）` 编号，再和 runbook 声称的范围对差集：多出来的要写进审计，
   少掉的要说明是「更早已完成」还是「其实没做」。同一串编号在不同任务池里含义不同
   （`D01` 在 v0.6.0 池是术语门禁，在 v0.12.0 池是文档事实门禁），引用时一律写成
   「D01（v0.6.0 池）」。
5. **区分四种「看起来一样」的状态，不许互相冒充。**
   - 代码合并 ≠ 已部署到生产；
   - 生产已跑新版本 ≠ 版本已发布（`v0.11.0` 生产在跑，但 tag 不存在）；
   - 本地/真库演练 ≠ 云端演练（`docs/operations/drills/*.sql` 只在本地 `001`–`033` 上跑过）；
   - 门禁全绿 ≠ 生产证据齐全（门禁只保证仓库内一致性）。

   易漂移的数字（用例条数、门禁条数、调用点数）只允许出现在**带日期的快照**里；
   living doc 一律指向命令或清单文件。

## 逐条核对步骤

```
枚举条目 → 找到实现（文件:行）→ 找到守它的面包屑（门禁/契约测试）
        → 找到执行记录（哪一天、什么命令、什么结果）→ 判档 → 缺口写进下一版任务池
```

- 「找到实现」要具体到文件，不接受模块名。
- 「找到门禁」时顺手做一次变异核对：门禁的判定条件删掉一条，看它是否真的变红。
- 核对过程中**发现的错误陈述要当场修**（历史上每次核对都发现了：写着「25 个迁移」而仓库有 33 个、
  英文文档教一种平台不允许的 cron、状态段引用错门禁名）。修完在审计里单列一节，
  说明这些是「核对副产物」而不是本版交付。
- 判定用语：写「未执行（需 X 权限）」，不写「预计下周」「基本完成」「应该没问题」。

## 文件骨架

两份文件都用同一套章节，缺哪节就说明哪件没做（v0.10.0 / v0.11.0 的缺口审计已按此结构）：

1. 标题 + 审计日期 + 审计范围（列出实际读过哪些文件与运行记录）
2. 结论（发布状态一句话 + 还差哪几条前置）
3. 范围口径核对（runbook / roadmap 声称 vs CHANGELOG 实际，写差集）
4. 退出标准逐条核对（表格：条件 / 证据 / 状态）
5. 缺口与交付物（表格：缺口 / 之前的问题 / 本次交付物 / 当前证据 / 状态）
6. 与上一版的差异（迁移数、不可逆操作、门禁、外部条件）
7. 未闭合项 → 下一版任务池（带编号与「为什么没关掉」）
8. 可复现验证（命令清单，逐条可跑）
9. 本审计自身无法核对的部分（需要凭据、隔离账号、外部控制台的那些）

## 与门禁的接线

- `pnpm check:release-docs` 只校验当前版本的 runbook / rollback / smoke 三份产物与 README、
  checklist 是否齐全，**不校验缺口审计是否存在**（它按版本号拼路径，历史上就是因为没人强制才断档）。
  所以把「本审计文件已产出」写进 `.github/RELEASE_CHECKLIST.md` 的冻结清单，
  由人工在冻结时勾选；断档一次就要在下一份审计里补一句「系列在 vX 之后断了」，让缺口可见。
- 审计里出现的每条命令，都必须是真实存在的 script（`check:docs` 与 `check:test-matrix`
  会拒绝文档里引用不存在的 `pnpm` 脚本）。
- 审计文件本身属于带日期的快照：发布之后不再回改它的状态列；
  后续进展写进 `docs/progress.md` 与下一版的审计。
