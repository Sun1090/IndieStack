# ADR-015: 秘密的哈希强度按熵判，不按字段名称判

日期: 2026-10-11
状态: 已接受

## 背景

仓库里此前有三处「服务端存一个可兑换的秘密」：

| 位置 | 秘密 | 熵 | 原哈希 |
|------|------|----|--------|
| `src/lib/actions/api-keys.ts` | API key secret | 192 位随机 | `sha256:<salt>:<hash>`（单轮） |
| `src/lib/repositories/marketing.ts` | 订阅 token | 192 位随机 | 单轮 SHA-256 |
| `src/lib/actions/recovery-codes.ts` | MFA 恢复码 | **≈39.6 位**（31 字符 × 8 位） | 单轮 SHA-256，**且无盐** |

前两处用快速哈希是**正确**的：192 位随机值的穷举空间与哈希速度无关。第三处名字里带
「code」、看起来和它们同类，实际熵低了 150 位以上——`31^8 = 852,891,037,441`，
一次库泄漏后攻击者可以**离线**跑完全部候选，而系统为此准备的两道防线（IP 限流、
需要已登录会话）都只在**在线**路径上起作用。同一用户 10 张码共享无盐哈希，
一次计算就能比对全部 10 行。而它承担的作用就是口令：**兑换成功会解绑全部 TOTP 因子**。

CodeQL 的 `js/insufficient-password-hash` 报在前两处（假阳性），**没有报第三处**。

## 决策

1. **哈希强度按秘密的可枚举空间判，不按它叫什么判。** 判据是
   `log2(字符集大小 ^ 长度)`，而不是字段名里有没有 `token` / `key` / `code`。
   高熵机器凭据（≥128 位）可用快速哈希（SHA-256，可加盐）；
   低熵、人可读写的秘密必须用内存困难的 KDF（scrypt / Argon2id / bcrypt）。
2. **恢复码改用 scrypt，每张码独立随机盐**：`scrypt$N$r$p$saltHex$derivedHex`，
   参数取 OWASP Password Storage Cheat Sheet 列出的五档同等最低防护之一
   `N=2^15 / r=8 / p=3`（另四档为 `2^17/p=1`、`2^16/p=2`、`2^14/p=5`、`2^13/p=10`，
   均 `r=8`；原文已抓取并逐字核对）。实现集中在 `src/lib/auth/recovery-code-hash.ts`。
3. **参数与盐记在存储字符串里，校验用行自己记录的值**，不用当前默认值。
   这样默认参数以后上调时不会把已生成码的用户锁在门外。
4. **形状解析不通过一律判否**（失败封闭），绝不回退成裸比较；
   KDF 抛错在认证路径上折叠成 `false`，不能让一次输错变成 500。
5. **存量不迁移**：64 位十六进制的裸 SHA-256 仍按旧分支可兑换，
   在用户重新生成时被整体替换，弱分支随使用自然消失。
6. `maxmem` 必须显式给（本实现按 `128·r·(N+p)` 的 2 倍，并有 64 MiB 下限）。
   **不带它就失败，而且失败是同步 `RangeError`**：`N=2^15/r=8/p=3` 的最小可用
   `maxmem` 实测为 **33,559,552 字节**（二分搜索得到），比 Node 默认 32 MiB
   （33,554,432 字节）多 **5120 字节**。闭合式在三组参数上都成立：`128·r·(N+p) + 2048`
   （`2^15/p=3` → 33,557,504+2,048、`2^13/p=10` → 8,398,848+2,048、
   `2^17/p=1` → 134,218,752+2,048）。贴着 `128·r·(N+p)` 本身**仍然失败**——
   那 2048 字节是 OpenSSL 的固定开销。

## 理由

- 放弃的方案是「统一都上 scrypt」。它更简单，但会让两处 192 位随机凭据的验证路径
  平白多出几百毫秒，并把 `api-keys` 的存储格式破坏掉。
- 放弃的方案是「写迁移把存量重哈希」。服务端没有明文，**不可能**重哈希；
  只能作废全部存量码，那等于在用户丢掉验证器的当口没收他的自救手段。
- **本 ADR 第一版在这里写错了一次，记录如下**：它声称「兑换是串行路径，`2^13/p=10`
  实测 10 张 3.24 秒，比 `2^15/p=3` 的 1.99 秒更慢」。按本实现重跑（每档独立进程、
  三轮取中位）实际是 **`2^13/p=10` 1.59 秒 < `2^15/p=3` 1.99 秒**——那个 3.24 秒不是实测，
  是把另一段脚本的读数记错之后当成了证据。**时间成本不构成选 `2^15/p=3` 的理由**，
  原来那条取舍整段作废。
- 现在保留 `N=2^15/p=3` 只剩一条理由，而且是内存不是时间：SMix 下界 `128·N·r` = 32 MiB
  （`2^13` 只有 8 MiB，这是算式），攻击方并行爆破要按次预留这份内存；
  独立进程 RSS 增量实测 +37 MiB 对 +13 MiB 印证了这个方向。OWASP 把五档列为同等防护，
  所以这是**取舍而非对错**：将来若要压函数内存峰值，`2^13/p=10` 是有据可选的降档，
  不是「更弱的草率选项」。

## 影响

- 新增约束：**任何新增的「服务端存可兑换秘密」都必须先量熵再选哈希**。
  审查时看字符集与长度（`src/lib/validations/mfa.ts` 是恢复码的单一来源），不看字段名。
- 低熵秘密的验证成本随候选数**线性**增长（新格式无法「先哈希一次明文再比」，
  因为盐在每一行里；实测 `2^15/p=3` 最坏兑换 = 10 次串行派生 = 1.99 秒）。
  `RECOVERY_CODE_COUNT` 因此是延迟上界的直接来源；
  将来调它要重测的是生成与兑换两条路径。若兑换路径变热，
  正确做法是把盐提成可索引列、先按 `(user_id, salt)` 缩小候选集，而不是调低参数。
- **并发的墙钟收益远小于直觉**：同一实现下 10 张并发派生 626ms（单次 208ms ⇒ 只有约
  3.3×，不是 10×），因为 libuv 默认线程池是 4；显式设 `UV_THREADPOOL_SIZE=16` 后降到
  480ms。任何「并发派生很便宜」的估算都要先量线程池。
- `pnpm check:supabase-security` 的信任证据清单同步登记 `verifyRecoveryCodeHash`。
  **这条登记的强度边界要说清**：它只回答「这个模块被授权做什么」，
  **不回答**「它现在是不是这样做的」——把兑换调用点整个退回旧的
  `timingSafeEqual(sha256(code))`，无论证据写成单值还是
  `["timingSafeEqual", "verifyRecoveryCodeHash"]` 都仍然绿
  （顶部那行 `import { …, verifyRecoveryCodeHash }` 本身就是真实代码，
  所以证据总能命中，实测过）。
  判据在 PR #240 之后已收紧为「剥注释 + 标识符词边界」匹配，
  **但这条登记的结论不变**——#240 堵住的是「注释里写一句就算证据」和
  「旧名字只剩在新名字的子串里」两条通道，堵住不了「import 还在、调用点已退回旧写法」。
  2026-10-12 在 #240 之上重测：调用点退回旧写法，`check:supabase-security` 仍然绿。
  **因此这条清单不能当回归防线用**；语义回退由 `src/lib/actions/recovery-codes.test.ts`
  的 3 条用例兜住。登记保持单值只因为它描述的是当前事实，不是因为它能防回退。
- 已知遗留矛盾：`supabase/migrations/013_mfa_recovery_codes.sql` 头部注释仍写
  「库中仅存 SHA-256 哈希」。该迁移被 `supabase/migration-manifest.json` 的 checksum 固定
  （immutable 34 条全绿），改写即红，因此**不回改历史迁移**，只在 ADR 与 CHANGELOG 登记。
